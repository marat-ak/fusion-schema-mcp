# Data-access security coverage — every catalog object vs the pod export (2026-10-01)

Offline analysis of the pod's data-security export (`data/security/*.csv`, saved 2026-10-01) against
release `v2027_03` (29,802 dictionary objects) and the corpus (`fusion_dev.work.*`). Produced by
`scripts/pipeline/security_coverage.sh v2027_03` → `data/security/coverage/` (objects.csv 29,802 rows,
conditions.csv 5,634, via_join_columns.csv 4,846, direct_privileges.csv 4,072, customer_layer.csv 58,
summary.json, samples.sql, report_tables.md + tables/). Read-only on every database; nothing shipped,
nothing committed. The design proposal is section 8; the open questions are section 10. **HCM is
section 11** (added later on 2026-10-01 after the user decision "add HCM profile"): the HCM_PROFILE
class of sections 2–3 no longer exists — HCM objects are now classified like everything else with an
`hcm=Y` flag; the re-run totals and the delta are in §11.6.

Binding rules applied throughout: **no pod id anywhere** in the outputs (object / function /
instance-set / grant ids are used only to join the four CSVs in memory; everything is named by
OBJ_NAME, FUNCTION_NAME, INSTANCE_SET_NAME, and the generator resolves names on the target pod);
**customer-created instance sets and customer objects are a separate layer**, excluded from every
"shipped" figure; **join-based security is strict only on a NOT NULL column** (dictionary
`columns.nullable = 0`), else leaky; **every classification carries its evidence**, nothing unmapped is
defaulted.

Findings about the export itself (all verifiable in `summary.json → export`):

1. **`GRANTS_WITH_PK_VALUE` is not suspicious, it is uninformative.** It is
   `SUM(instance_pk1_value IS NOT NULL)` and equals 99% of GRANTS for every instance type (GLOBAL
   28,716 / 29,007; SET 89,206 / 89,907; INSTANCE 1,124 / 1,264). Fusion stores a placeholder in
   `INSTANCE_PK1_VALUE` on non-INSTANCE grants (the EBS/Fusion `'*NULL*'` convention); only
   `INSTANCE_TYPE` discriminates. One-line pod check: `SELECT instance_type, instance_pk1_value, COUNT(*)
   FROM fnd_grants WHERE instance_type <> 'INSTANCE' GROUP BY 1, 2`. The ~1% genuinely NULL rows are
   worth a look in the same query (grants created by a different writer).
2. **72 predicates carry a spurious leading apostrophe** added by the CSV writer to values that begin
   with whitespace/newline (Excel-style protection). `DBMS_LOB.GETLENGTH` (PRED_LEN) proves it: the
   text is exactly one character too long and starts with `'`. The loader strips it (count recorded as
   `apostrophe_artefact_stripped: 72`; after the strip every PRED_LEN matches). Kept, it would break
   the SQL.
3. **130 objects have `OBJ_NAME ≠ DATABASE_OBJECT_NAME`**: 122 are customer objects (App Composer
   `_c` and `XXKD_*` objects registered on `HZ_REF_ENTITIES` / `MKT_REF_ENTITIES` / `ZCA_REF_ENTITIES` /
   `FND_VS_VALUES_VL` …), and 8 are Oracle's (`EGP_SYSTEM_ITEMS_B` → `EGP_SYSTEM_ITEMS_B_V`,
   `EGO_CATALOG_GROUP` → `EGP_ITEM_CLASSES_B`, `MSC_ORGANIZATIONS` → `MSC_ORGANIZATION_SUBINV_V`,
   `FUN_WORKFLOW_USERS` → `_V`, `MSC_SYSTEM_ITEMS` …). Catalog matching and the isolated form must
   use `DATABASE_OBJECT_NAME`; the grant lookup must use `OBJ_NAME`. Both are kept.
4. **`GRANTS_WITH_CONTEXT = 0` on every link**: no grant on this pod is context-scoped, so the
   `(gnt.CONTEXT_NAME IS NULL OR gnt.CONTEXT_VALUE LIKE FND_GLOBAL.GET_CONN_DS_ATTRIBUTE(…))` clause
   is kept for generality but is never exercised here (not pod-verified on a pod that uses it).
5. **2,554 links (13%) have USER grantees** (`GRANTEE_TYPE = 'USER'` or mixed): direct user grants on
   ZMM_NOTES, PER_ALL_PEOPLE_F, HZ_PARTIES, ESS_REQUEST_HISTORY … (mostly `read`/`update`/`delete`).
   Nothing to ship, but the condition's `OR gnt.GRANTEE_KEY = FND_GLOBAL.USER_GUID` branch is what
   honours them.
6. **377 links carry grant parameters** (`PARAMETER1…`); 185 instance sets reference
   `&GRANT_ALIAS.PARAMETER1` (26 `PARAMETER2`, 5 each `PARAMETER3…7`). They resolve to `gnt.PARAMETERn`
   at run time — no literal is needed.
7. **4 instance sets are active but have no grant link** (`EGOITEMEFFVLEGO1` on EGO_ITEM_EFF_VL,
   `EGO_ITEM_REVISION_EFF_VL`, `EGO_ITEM_SUPPLIER_EFF_B`, `_VL`): their objects report 22 active grants
   but **0 registered privileges**, i.e. grants whose menu carries no function — unusable, classed
   REGISTERED_NO_GRANT ("grants carry no privilege").
8. **23 registered objects have no grant link** (19 with GRANTS_ACTIVE 0 + the 4 above); 18 of them
   are in our dictionary (13 tables / 5 views) → REGISTERED_NO_GRANT. The user's "13 expected" was the
   FND_TABLES-based count; the object-based count is 23 (18 in the dictionary).
9. **9 granted objects have a DB object that is not in our dictionary** (ESS_REQUEST_HISTORY,
   ACN_FEATURE_B, PAY_TRANSACTION_TEMPLATES, PER_CHK_TASK_GROUPS_V, PSC_LNP_BUS_OWNER_CRED,
   PSC_PRG_APPLICATION, SVC_CATEGORIES, WLF_CATALOG_LEARNING_ITEMS_VL, WLF_LEARNING_INITIATIVES_VL) —
   a dictionary gap, not a security one.
10. **15 DIRECT objects name PK columns our dictionary does not have** (CSO_CHANNEL, CSO_SITE, CSO_TAG,
    CSO_WORKFLOW_STEP, DOS_SUPPLY_LINES, FV_BE_LEVEL_OPERATIONS_V, HRM_ASSIGNMENTS_V, HRM_POOLS_V,
    JE_ES_MODELO_190_ALL, PJS_PPC_REP_ASSOCIATIONS_VL, POZ_LOOKUP_CODES, PSC_INS_INSPECTION_CHKLIST,
    PSC_INS_INSPECTION_CL_ITEM, ZPM_PROGRAM_BENEFITS, ZSF_DS_PARTICIPANT_RF_DN_VIEW): the isolated
    form cannot be built for them from the dictionary (alias form only, flagged).
11. **The 1,002 granted objects land as**: 534 DIRECT catalog objects, 337 HCM_PROFILE (HCM-prefixed,
    excluded by design), 122 customer objects (customer layer), 9 not in the dictionary (DIRECT shows
    545 because 11 further dictionary objects are reached through a registered object whose DB name
    differs: the 9 customer-only carriers — FND_VS_VALUES_VL and 8 `*_REF_ENTITIES` — and the 2
    `db_object_differs` objects EGP_SYSTEM_ITEMS_B and MSC_SYSTEM_ITEMS).
12. **`MKT_IMP_MAP` is in `v2027_03.table_disallowed`** (unresolved ORGANIZATION_ID on an unused object)
    **and registered + granted in FND_OBJECTS** — DIRECT wins here (its SET grants are customer-made,
    its GLOBAL grants Oracle's). The release fact is stale for it.
13. `oracle_datasec_policies.csv` (150 URDA sets) is a strict subset of 03 (150 of 150 `USES_URDA = Y`
    rows present).

## 3. Per class

### DIRECT (545: 526 tables, 19 views; 406 corpus-used)

- 4,072 privileges on the 545 objects (median 5 per object, max 192 on FUN_ALL_BUSINESS_UNITS_V from
  26 product prefixes AP_/AR_/CN_/DOO/EXM/GMS/IBY/IEX/JA_/JG_/PJB/PJC/PJF/PJS/PON/POR/QP_/ZX_ …).
  `read` exists on 463 of the 545 (85%); on those objects 2,051 of the 2,924 other privileges (70%)
  carry a different instance-set / grant-type profile than `read`, and only 2 objects have `read` alone
  — `read` is not a usable default.
- **Isolation**: 2,081 of the 4,072 privileges (on 365 objects) have ≥1 instance set without
  `&TABLE_ALIAS` → the isolated form `(alias.pk…) IN (SELECT sec$.pk… FROM <db object> sec$ WHERE …)`
  is mandatory for them even when the table stands alone. 965 privileges have USER grantees; 251 use
  grant parameters.
- **Two objects secure a different DB object than their name** (`db_object_differs`):
  `EGP_SYSTEM_ITEMS_B` (grants evaluated on `EGP_SYSTEM_ITEMS_B_V`) and `MSC_SYSTEM_ITEMS` → the
  isolated form through the DB object is the only correct form for them.
- **9 DIRECT objects are customer-only** (their only granted registration is a customer object):
  `FND_VS_VALUES_VL` (via `XXKD_COMPANY_SECURITY_RULE`, 7 sets, 1,749 corpus statements use the view)
  and the 8 `*_REF_ENTITIES` carriers of the `_c` objects. For the shipped catalog they are
  UNSECURABLE; they become DIRECT only with the customer layer loaded (section 5).
- 6 Oracle objects additionally carry customer-created sets (FND_VS_VALUES_VL, MKT_IMP_JOBS,
  MKT_IMP_MAP, MKT_IMP_OBJECTS, MSC_ORGANIZATION_SUBINV_V, ZCA_OBJECTS) — the generator drops those
  sets from the shipped condition and reports them.
- **19 views**, all with base lineage from the corpus (`work.sql_unit` view text → `r_tables`), e.g.
  FUN_ALL_BUSINESS_UNITS_V ← HR_ALL_ORGANIZATION_UNITS_F_VL + HR_ORGANIZATION_INFORMATION_X +
  HR_ORG_UNIT_CLASSIFICATIONS_X; EGP_SYSTEM_ITEMS_B_V ← EGP_SYSTEM_ITEMS_B + EGP_ITEM_ORG_ASSOCIATIONS;
  PJF_PROJECTS_ALL_VL ← _B + _TL; CST_COST_ORGS_V ← HR_* tables. No literal-id set survives in any
  DIRECT object's shipped condition (`has_literal_ids: []`).

### 8.1 Shipped tables (release schema `v<ver>`, built by a new stage from the export; names only)

| `sec_privilege` | `obj_name, privilege` | `display_name`, `description`, `grant_global`/`grant_set`/`grant_instance` flags, `needs_isolation`, `uses_grant_parameter`, `uses_session_util`, `has_user_grantees`; `roles_hint` (a count, not an id — ship or drop: question 8) |

`table_security` stays as it is (context column → ref object/column, variant, confidence); the
VIA_JOIN facts are derived at serve time from `table_security` ⋈ `columns.nullable` ⋈ `sec_object` ⋈
`sec_area_privilege` — no second copy. `table_grants` (ids from the demo pod, mined triples) is
**legacy** under rule 1 (`object_id` / `function_id` / `instance_set_id` columns) — removed, its two
named triples are already in `sec_grant_link` (GL_LEDGERS / GLLEDGERSSTD, FUN_ALL_BUSINESS_UNITS_V /

`book_via_controls`, `item_inv_union`, `role_correlation`, `grant_wrapper`) become legacy too once
the reference-object condition replaces them (question 1).

### 8.2 `getDataAccessPredicate(table, alias, privilege?, area?, joined?)` — assembly per class

1. `sec_coverage[table].class` decides the branch; HCM_PROFILE / DISALLOWED / REGISTERED_NO_GRANT /
   UNSECURABLE return the class + reason (as DISALLOWED does today) — never an empty predicate presented
   as "open".
2. **Privilege resolution** (DIRECT and every VIA_JOIN / VIA_PARENT hop): explicit `privilege` →
   else `sec_area_privilege(area, context) = chosen` → else **`needs-input`** with the candidate list
   (display names, descriptions) — `read` is never assumed.
3. **DIRECT**: `compact(obj_name, privilege, alias)` =
   `EXISTS (SELECT NULL FROM FND_GRANTS gnt WHERE gnt.OBJECT_ID = (SELECT … WHERE obj_name = :obj) AND
   GRANT_TYPE = 'ALLOW' AND dates AND (session-role EXISTS OR GRANTEE_KEY = USER_GUID) AND EXISTS
   (compiled menu function = :privilege by name) AND context clause AND (INSTANCE_TYPE = 'GLOBAL' OR
   (INSTANCE AND INSTANCE_PK1_VALUE = TO_CHAR(alias.pk1) …) OR (SET AND (… OR (INSTANCE_SET_ID IN
   (names …) AND <template with alias>) …))))` — branches only for the grant types the link table has;
   identical templates merged into one name list; customer-created and literal-id sets dropped and
   reported. **Isolated form** `(alias.pk…) IN (SELECT sec$.pk… FROM <database_object_name> sec$ WHERE
   compact(…, 'sec$'))` whenever the privilege `needs_isolation`, or `joined` is true, or
   `database_object_name ≠ table`, or the object has >1 PK column; alias form otherwise. Objects whose
   PK columns are missing from the dictionary (15) get the alias form + a note.
4. **VIA_JOIN**: for every context column (all AND-ed, as today): `alias.col IN (SELECT sec$.ref_col FROM
   <ref db object> sec$ WHERE compact(ref_obj, privilege_for(area, context), 'sec$'))`; nullable →
   `(alias.col IS NULL OR …)` + the leaky note. The privilege is per (area, context), so AP_INVOICES_ALL
   asks for AP_x on BU and GL_y on LEDGER (or the chosen rule says the secondary context is skipped —
   question 3).
5. **VIA_PARENT**: `alias.join_col IN (SELECT p.pk FROM <parent> p WHERE <parent's own condition with
   alias p>)` recursively through the recorded chain (DIRECT parent → compact; VIA_JOIN parent → its
   column conditions); nullable join column → `IS NULL OR` + leaky; depth and chain verdict in the notes.
6. Output keeps the spec §6 shape — the secured CTE `<alias>_sec AS (SELECT /*+ INLINE */ t.* FROM T t
   WHERE <conditions>)` — plus `class`, `privilege {name, source: explicit | area-map | needs-input,
   candidates}`, `conditions[] {column, sql, strictness}` and `notes[]`. The text is user-independent
   (every lookup resolves at run time in the pod session) and cacheable per (table, privilege, alias).

### 8.3 Area → privilege map

`sec_area_privilege` is curated, not derived: the prefix filter is the candidate generator (section 7),
the user approves `chosen` rows per (area, context). Rows the map needs first, from the corpus-used
tables: AP/BU, AR/BU, AR/SET, GL/LEDGER, GL/DAS, INV/INV_ORG, CST/COST_ORG, FA/BOOK, PJC/BU, PJF/BU, and
the explicit decisions for PO (parent PO_HEADERS_ALL privilege), POZ, XLA, MSC, and every secondary
context (LEDGER on non-GL tables, PRJ_ORG, ITM_ORG, SET on non-setup tables).

### 8.4 Customer layer

Same four tables under `customer.` (`customer.sec_object`, `sec_privilege`, `sec_instance_set`,
`sec_grant_link`) + `customer.sec_area_privilege` for overrides, loaded by an admin upload of the
customer pod's export (CSV, same queries; the loader strips the apostrophe artefact and keeps only
`CREATED_BY ≠ SEED` sets, customer objects, and the links that reference them; seed rows are diffed
against the shipped set → drift report "on pod but not shipped / shipped but not on pod"). At
generation time the links of (object, privilege) are the union shipped ∪ customer; a customer
`sec_area_privilege` row with the same key overrides the shipped `chosen` row; a customer-only object
(FND_VS_VALUES_VL via XXKD_COMPANY_SECURITY_RULE) turns from UNSECURABLE into DIRECT only when the
layer is loaded. Nothing in `customer.` ever reaches a release.

### 8.5 What the plugin skill (data-access-security) must change

- **Privilege by report area**: the skill names the report's business area and passes `area` (or an
  explicit `privilege`) to the tool; on `needs-input` it asks ONE question listing the candidates with
  their display names and never falls back to `read`.
- **Isolated form in joins**: when the secured table is not the only table in the FROM, pass
  `joined: true`; the tool then emits the isolated form (and the secured CTE keeps the alias scope).
- **Wording**: every Data access line says the class, the privilege, the strictness ("ORG_ID strict;
  EXPENDITURE_ORGANIZATION_ID leaky — NULL rows are not restricted") and **"not pod-verified"** until
  `sec_meta.probe_compact_generator = pass`; HCM objects are reported as "secured by HCM security
  profiles — not supported here"; REGISTERED_NO_GRANT as "registered, no grant on this pod — cannot be
  secured, not open".
- The kernel rule's gate (createDataModelFile / setDatasetSql / runSql require the tool) is unchanged.

## 10. Open design questions (the user decides; nothing below is implemented)

1. **Replace or add**: the registered-object condition (role + privilege + instance sets, Oracle's own
   semantics) subsumes the v2027_03 URDA templates (`template.direct` etc. = the inner STD set without
   role scoping). Recommendation: replace; the URDA templates and `table_grants` become legacy to
   remove in the same release.
2. **Area → privilege where the prefix filter is empty** (1,921 VIA_JOIN tables; PO / POZ / XLA / MSC /
   CST-on-INV_ORG, every secondary context): curate per product, or restrict generation to the primary
   context and refuse the rest with `needs-input`?
3. **Several context columns per table**: AND every column with its own privilege (current rule,
   e.g. AP_INVOICES_ALL = AP_x on BU AND GL_y on LEDGER AND leaky PRJ_ORG), or primary context only with
   the others reported?
4. **PO lines/locations/distributions**: VIA_JOIN on PRC_BU_ID (classifier precedence) or VIA_PARENT of
   PO_HEADERS_ALL with PO_VIEW_PO_DOC_TXN_DATA (Oracle's own model)? Generalises to: prefer a DIRECT
   parent over a BU column when both exist.
5. **VIA_PARENT acceptance**: FK-only (1,580) or also the 226 dominant corpus joins; emit leaky chains
   (689) with `IS NULL OR`, or refuse them?
6. **HCM_PROFILE** (5,580; 337 registered + granted with profile-compiled sets): confirm the exclusion
   stays — those sets are per-pod compiled constants and cannot ship. **Decided 2026-10-01: HCM is
   in** — see §11 (the profile-compiled sets are indeed unshippable by name; the secured-list views are
   the way through).
7. **Customer-only DIRECT objects** (FND_VS_VALUES_VL + 8 `*_REF_ENTITIES`): UNSECURABLE in the shipped
   set, DIRECT with the customer layer — confirm.
8. **Pod statistics** (`ROLES_DISTINCT`, grant counts, corpus usage) in the shipped tables: ship as
   hints (`roles_hint`) or drop (they are not ids but they are pod facts)?
9. **Files**: the export CSVs (7.7 MB, `data/security/`) are not matched by the repo's `data/*.csv`
   ignore and would be committed; the coverage outputs (objects.csv 29.8k rows, conditions.csv with the
   full predicates) likewise — commit, ignore, or Tier B?
10. **Dictionary gaps surfaced**: 9 granted objects and 15 PK columns absent from v2027_03, and
    MKT_IMP_MAP's stale disallow — fold into the next catalog release?

**Verdict — generic text, pod-specific linkage.** The predicate texts evaluate per session user on any
pod (HRC_SESSION_UTIL, PER_MANAGER_HRCHY_DN, PER_SHARE_INFORMATION, PER_ALL_ASSIGNMENTS_M). What is
pod-specific is the *link*: a restricted data role's grant points at `HCM_<type>_<id>` — a set name that
does not exist on any other pod and is not in the shipped name list — and a custom profile (department
list, org/position hierarchy, LDG/payroll list, custom restriction text) compiles pod ids into the text.
Consequence for the compact generator (sample 5, `samples.sql`): on this pod it emits `GLOBAL OR
(PERALLPEOPLEF_S AND (1 = 2))` — correct for *View All* users, and **fails closed (0 rows), not open, for
a restricted user or a job-role-only user**. Oracle's own answer for BIP is a different mechanism:
the secured list views (§11.3).

### 11.4 Design proposal — HCM in `getDataAccessPredicate`

(a) **DIRECT (337) — do NOT emit the compact FND_GRANTS condition for `hcm=Y` objects.** It needs no
isolation beyond the usual rules and has no pod id in it, but it can only ever see GLOBAL grants, the
`_S` placeholder (`1=2`) and the 81 seed conditions; it is blind to every `HCM_<type>_<id>` set a
restricted or custom profile would link, and to the job-role-only case — it fails closed, which is
safe but useless on exactly the pods that need security. Emit instead:
- anchor with a secured list view (the 12 of §11.2 + PER_PERSONS, CMP_SALARY): `alias.<key> IN (SELECT
  <key> FROM <SECURED_LIST_V>)` (76 chars; sample 6) — or tell the skill to read the secured list view
  in place of the base table (Oracle's own guidance); the privilege is implicit (the view's policy);
- any other registered HCM object with an HCM context column (237 of 337): the VIA_JOIN form (b);
- the 100 without one: VIA_PARENT through their recorded parent when it is HCM-secured (HRT_PROFILE_ITEMS
  → HRT_PROFILES_B.PERSON_ID, PAY_RUN_RESULTS → PAY_PAYROLL_REL_ACTIONS.PAYROLL_RELATIONSHIP_ID …), else
  `needs-input` with the object's seed conditions listed (WLF learning visibility, HRC transaction
  profile, BEN setup) — never the compact form presented as complete;
- the 15 objects whose grant kinds carry no placeholder and no profile set (12 GLOBAL-only + 3
  seed-condition-only) are the only HCM objects where the compact form is complete on this pod; keep
  them compact only if the PER_SECURING_OBJECTS extract (e) shows no securing object maps them.

(b) **VIA_JOIN through the anchors** — `alias.col IN (SELECT col FROM <secured list>)`, `(alias.col IS
NULL OR …)` + leaky note when nullable (900 of 1,601 columns; 596 tables have ≥1 leaky column — the
primary is strict on 554). Several HCM columns on one table: primary only (the PERSON row secures the
assignment rows; AND-ing LDG + PERSON on PAY tables double-filters) — the other contexts are reported
as notes (question 11.7-2). Anchors without a secured list: one hop more, `alias.PAYROLL_RELATIONSHIP_ID
IN (SELECT PAYROLL_RELATIONSHIP_ID FROM PAY_PAY_RELATIONSHIPS_DN WHERE PERSON_ID IN (SELECT PERSON_ID
FROM PER_PERSON_SECURED_LIST_V))` (19 primary tables), PERIOD_OF_SERVICE_ID likewise via
PER_PERIODS_OF_SERVICE.PERSON_ID (0 primary tables — it never wins). The privilege family per anchor
(for the `direct_privileges.csv` / `area → privilege` map, if the compact form is ever wanted for HCM):
PER_REPORT_PERSON_DATA (50 roles), PER_REPORT_PUBLIC_PERSON_DATA (62) / PER_REPORT_PERSON_DEFERRED_DATA
(4) on PER_PERSONS, PER_REPORT_ASSIGNMENT_DATA (15) + PER_REPORT_PERSON_ASSIGNMENT_DATA (13) +
CMP/ANC/HRA/HRG_REPORT_* on PER_ALL_ASSIGNMENTS_M, PER_REPORT_DEPARTMENT_DATA (47) /
PER_REPORT_LEGAL_EMPLOYER_DATA (19), PER_REPORT_POSITION_DATA (49), PER_REPORT_LEGISLATIVE_DATA_GROUP_DATA
(21), PAY_REPORT_PAYROLL_DEFINITION_DATA (20), PER_REPORT_HR_JOB_DATA (47), PER_REPORT_ASSIGNMENT_GRADE_DATA
(44), PER_REPORT_LOCATION_DATA (47), PAY_REPORT_PAYROLL_RELATIONSHIP_DATA (16) /
PAY_REPORT_PERSON_PROCESS_RESULTS_DATA (17), PER_REPORT_WORK_RELATIONSHIP_DATA (3),
PAY_REPORT_PAYROLL_FLOW_DATA (12), CMP_REPORT_SALARY_DATA (8), HRT_REPORT_TALENT_PROFILE_DATA (5),
PER_REPORT_WORKER_DOCUMENTS_OF_RECORD_DATA (8). One choice remains for PERSON_ID: full person
(PER_PERSON_SECURED_LIST_V) vs public person (PER_PUB_PERS_SECURED_LIST_V, directory-style reports) —
default full person, public person as an explicit option.

(c) **Unsecurable** after (a)+(b): the 4,059 (1,599 corpus-used, mostly lookups / setup / translations
with no key), the 100 DIRECT without key or HCM parent (above), and — out of this scope but now visible
— **non-HCM objects with PERSON_ID** (AP expenses, PJF resources, POZ …): the generic classifier gives
them BU/LEDGER contexts, not a person context; whether a person secured list must be AND-ed there is a

```sql
-- 08 security profiles per type (flags only): person / org / position / LDG / payroll
SELECT 'PERSON' profile_type, PERSON_SECURITY_PROFILE_ID profile_id, NAME, VIEW_ALL, ENABLED_FLAG, SEED_DATA_SOURCE,
       ACCESS_TO_OWN_RECORD || '/' || SECURE_BY_MGR_HIERARCHY || '/' || SECURE_BY_DEPARTMENT || '/' || SECURE_BY_LEGAL_EMPLOYER || '/' ||
       SECURE_BY_BUSINESS_UNIT || '/' || SECURE_BY_POSITION || '/' || SECURE_BY_LDG || '/' || SECURE_BY_PAYROLL || '/' || SECURE_BY_PERSON_TYPE || '/' ||
       SECURE_BY_AOR || '/' || SECURE_BY_CUSTOM_RESTRICTION restrictions, CUSTOM_RESTRICTION_TEXT
FROM   PER_PERSON_SECURITY_PROFILES
UNION ALL SELECT 'ORG', ORG_SECURITY_PROFILE_ID, NAME, VIEW_ALL, ENABLED_FLAG, SEED_DATA_SOURCE,
       SECURE_BY_ORG_CLASS || '/' || SECURE_BY_ORG_HIERARCHY || '/' || SECURE_BY_ORG_LIST || '/' || SECURE_BY_LOCATION, NULL FROM PER_ORG_SECURITY_PROFILES
UNION ALL SELECT 'POSITION', POSITION_SECURITY_PROFILE_ID, NAME, VIEW_ALL, ENABLED_FLAG, SEED_DATA_SOURCE,
       SECURE_BY_POSITION_HIERARCHY || '/' || SECURE_BY_POSITION_LIST || '/' || SECURE_BY_DEPARTMENT || '/' || SECURE_BY_JOB, NULL FROM PER_POSITION_SECURITY_PROFILES
UNION ALL SELECT 'LDG', LDG_SECURITY_PROFILE_ID, NAME, VIEW_ALL, ENABLED_FLAG, SEED_DATA_SOURCE, NULL, NULL FROM PER_LDG_SECURITY_PROFILES
UNION ALL SELECT 'PAYROLL', PAY_SECURITY_PROFILE_ID, NAME, VIEW_ALL, ENABLED_FLAG, SEED_DATA_SOURCE, NULL, NULL FROM PAY_PAY_SECURITY_PROFILES;
-- 09 profile-compiled instance sets with their grant links (which data role / privilege uses which HCM_<type>_<id> set)
SELECT o.OBJ_NAME, ois.INSTANCE_SET_NAME, ois.INSTANCE_SET_DESCRIPTION, g.ROLE_NAME, ff.FUNCTION_NAME privilege, COUNT(*) grants
FROM   FND_OBJECT_INSTANCE_SETS ois JOIN FND_OBJECTS o ON o.OBJECT_ID = ois.OBJECT_ID
JOIN   FND_GRANTS g ON g.INSTANCE_SET_ID = ois.INSTANCE_SET_ID AND g.GRANT_TYPE = 'ALLOW' AND (g.END_DATE IS NULL OR g.END_DATE >= SYSDATE)
JOIN   FND_COMPILED_MENU_FUNCTIONS cmf ON cmf.MENU_ID = g.MENU_ID JOIN FND_FORM_FUNCTIONS ff ON ff.FUNCTION_ID = cmf.FUNCTION_ID
WHERE  ois.INSTANCE_SET_NAME LIKE 'HCM\_%' ESCAPE '\' GROUP BY 1, 2, 3, 4, 5 ORDER BY 1, 2, 4;
```
06 is the one that matters: it replaces the curated `HCM_CONTEXTS` for the registered objects with
Oracle's own object → securing-object → column map (and tells which of the 100 keyless DIRECT objects
HCM secures through what); 07/08 tell *View All* from restricted without a session; 09 is the H3 probe
